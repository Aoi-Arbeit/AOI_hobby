### 1.2 技術スタック（確定）

| レイヤー | 技術 | 選定理由 |
|---------|------|---------|
| フロントエンド | React 18 + TypeScript | 型安全・エコシステムの充実 |
| チャートライブラリ | TradingView Lightweight Charts | FX向け高性能チャート描画 |
| 状態管理 | Zustand | シンプルで軽量、WebSocket連携が容易 |
| スタイリング | Tailwind CSS | レスポンシブ対応が高速 |
| バックエンド | Python 3.12 + FastAPI | 非同期処理・高パフォーマンス・型安全 |
| WebSocket | FastAPI WebSocket（Starlette） | FastAPIとシームレスに統合 |
| タスクキュー | Celery + Redis | 注文監視の非同期バックグラウンド処理 |
| データベース | PostgreSQL 16 | ACID保証・JSON型サポート |
| キャッシュ | Redis 7 | レートキャッシュ・Celeryブローカー兼用 |
| リバースプロキシ | Nginx | HTTPS終端・WebSocket対応 |
| ホスティング | Railway（バックエンド）/ Vercel（フロント） | デプロイ容易・スケール対応 |
| タイムゾーン処理 | Python: `zoneinfo` / JS: `date-fns-tz` | JST/UTC変換・サマータイム自動換算 |

### 1.3 レート配信フロー

```
外部API (OANDA)
    │ 1秒ごとにポーリング or WebSocketで受信
    ▼
サーバー（Redis に最新レートをキャッシュ）
    │ WebSocketで全クライアントにブロードキャスト（1〜3秒間隔）
    ▼
各ブラウザ（リアルタイム表示・損益計算）

※ 外部APIダウン時: Redisキャッシュの最終レートを表示 + ユーザーへ通知
```

#### SCR-05 注文パネル（モーダル）詳細

注文タイプ別フォーム構成：

| 注文タイプ | 表示フィールド |
|-----------|-------------|
| 成行（Market） | 通貨ペア / 方向(Buy\|Sell) / ロット / レバレッジ / SL / TP |
| 指値（Limit） | 上記 + 指値レート |
| 逆指値（Stop） | 上記 + 逆指値レート |
| OCO | 上記 + 指値レート + 逆指値レート（同時設定） |
| IFD | エントリー注文設定 + 決済注文設定（2段階フォーム） |
| IFO | エントリー注文設定 + SL/TP（OCO形式）（3段フォーム） |

各フォームに「注文タイプ解説」ボタンを配置し、タップするとモーダル内でそのタイプの説明を表示する。

| カラム名 | 型 | NULL | 説明 |

| `id` | UUID | NOT NULL | 主キー（PK） |

| `updated_at` | TIMESTAMPTZ | NOT NULL | 更新日時 |

> **計算フィールド（DBには保存しない・API側で算出）**
> - `equity`（有効証拠金） = `balance` + 全保有ポジションの含み損益合計
> - `margin_level`（証拠金維持率） = `equity` ÷ 必要証拠金合計 × 100

## 5. WebSocket通信設計

### 5.1 接続仕様

| 項目 | 内容 |
|------|------|
| エンドポイント | `wss://api.fxpractice.app/v1/ws` |
| 認証 | 接続時にJWTをクエリパラメータで送信（`?token=<jwt>`） |
| プロトコル | JSON形式のメッセージング |
| Ping/Pong | 30秒間隔でサーバーからPing。応答なしで60秒後に切断 |

### 5.2 サーバー → クライアント イベント

| イベント名 | 説明 | 主なペイロード |
|-----------|------|-------------|
| `rate.update` | レート更新（1〜3秒間隔） | `symbol`, `bid`, `ask`, `spread`, `timestamp` |
| `position.pnl_update` | 保有ポジションの含み損益更新 | `position_id`, `unrealized_pnl`, `margin_level` |
| `order.filled` | 注文約定通知 | `order_id`, `filled_price`, `slippage_pips`, `position_id` |
| `order.cancelled` | 注文キャンセル通知（OCO等） | `order_id`, `reason` |
| `position.loss_cut` | ロスカット発動通知 | `position_id`, `exit_price`, `net_pnl` |
| `connection.status` | 接続状態通知 | `status` (`connected` / `reconnected` / `rate_source_degraded`) |
| `sync.response` | 再接続後の状態同期レスポンス | `positions`, `orders`, `balance`, `equity` |

### 5.3 クライアント → サーバー イベント

| イベント名 | 説明 | ペイロード |
|-----------|------|----------|
| `subscribe.rates` | レート受信する通貨ペアを指定 | `symbols: ["USDJPY", "EURUSD"]` |
| `sync.request` | 再接続後に最新状態を要求 | なし |

### 5.4 オフライン・再接続フロー

```
クライアント              サーバー
    │                       │
    │ ←── Ping ─────────── │ (30秒間隔)
    │                       │
    │ 通信断（ネットワーク障害）
    │                       │
    │ ① 3秒以内に切断を検知  │
    │ ② 画面にオーバーレイ表示│
    │ ③ 損益・レートを凍結   │
    │                       │
    │ ── 指数バックオフ再接続試行 ──
    │  (1s → 2s → 4s → ... → 30s)
    │                       │
    │ ── WSS接続 ──────────► │
    │ ── sync.request ─────► │
    │                       │ 注文マッチングエンジンは継続稼働
    │ ◄── sync.response ─── │ (positions, orders, balance, equity)
    │                       │
    │ ④ 画面を最新状態に更新  │
    │ ⑤ オーバーレイ解除     │
    │ ⑥ 「同期完了」トースト  │
```

## 6. 外部API連携設計

### 6.1 リアルタイムレート（OANDA API）

| 項目 | 内容 |
|------|------|
| 利用API | OANDA v20 Streaming API |
| 取得方法 | Streamingエンドポイント（常時接続型） |
| 取得通貨ペア | USD_JPY / EUR_JPY / EUR_USD / GBP_USD / AUD_JPY / CHF_JPY（初期6ペア） |

### 6.2 ヒストリカルデータ（Alpha Vantage）

| 項目 | 内容 |
|------|------|
| 利用API | Alpha Vantage FX Daily / Intraday |
| 用途 | 初期データ投入・エリオット波動練習用の過去データ |
| 取得間隔 | バッチ処理（Celery）で日次更新 |
| 保存先 | `rate_snapshots` テーブル（月次パーティション） |
| キャッシュ | 1時間以上前のヒストリカルはDBから直接応答（Redis不使用） |

### 6.3 経済指標（Investing.com RSS / TradingEconomics API）

| 項目 | 内容 |
|------|------|
| 利用ソース | TradingEconomics API（または Investing.com RSS） |
| 取得間隔 | 1時間ごとにCeleryバッチで `economic_events` を更新 |
| 実績値更新 | 指標発表後、`actual` カラムをリアルタイムで更新 |

## 7. エラーハンドリング設計

### 7.1 HTTPエラーコード定義

| HTTPステータス | エラーコード | 説明 |
|--------------|------------|------|
| 400 | `VALIDATION_ERROR` | リクエストパラメータ不正 |
| 400 | `INSUFFICIENT_MARGIN` | 証拠金不足で注文不可 |
| 400 | `INVALID_ORDER_TYPE` | 不正な注文タイプの組み合わせ |
| 401 | `UNAUTHORIZED` | 未認証・トークン期限切れ |
| 403 | `FORBIDDEN` | 権限なし（他ユーザーのリソース操作等） |
| 404 | `NOT_FOUND` | 指定リソースが存在しない |
| 409 | `ORDER_ALREADY_FILLED` | 約定済み注文のキャンセル試行 |
| 409 | `POSITION_ALREADY_CLOSED` | 決済済みポジションの再決済試行 |
| 429 | `RATE_LIMIT_EXCEEDED` | レートリミット超過 |
| 503 | `RATE_SOURCE_UNAVAILABLE` | 外部APIからのレート取得不可 |
| 500 | `INTERNAL_ERROR` | サーバー内部エラー |

### 7.2 注文エンジンのエラーハンドリング

| エラーケース | 処理方針 |
|------------|---------|
| 約定処理中にDBエラー | トランザクションをロールバック。注文は `pending` のまま保持し、再試行キューに積む |
| スリッページ計算失敗 | スリッページなし（0pips）で約定し、監査ログに記録 |
| ロスカット処理失敗 | アラートをログ出力。手動対応フローへ（運用フェーズで自動通知を整備） |
| OCO対注文のキャンセル失敗 | リトライ3回後も失敗した場合は管理者アラートを発報 |

## 8. セキュリティ設計

### 8.1 認証・認可フロー

```
クライアント                  サーバー
    │                           │
    │── POST /auth/login ──────► │
    │                           │ パスワード検証（bcrypt）
    │◄── access_token（15分）──  │
    │◄── refresh_token（7日）──  │ HTTPOnly Cookie に保存
    │    (Cookie: Secure/HTTPOnly)│
    │                           │
    │── API Request ───────────► │
    │   Authorization: Bearer    │ JWTの署名・有効期限を検証
    │                           │
    │── POST /auth/refresh ────► │ refresh_token を検証
    │◄── 新しい access_token ──  │
```

### 8.2 セキュリティ対策一覧

| 対策 | 実装内容 |
|------|---------|
| パスワードハッシュ | bcrypt（コストファクター: 12） |
| SQL インジェクション対策 | SQLAlchemy ORM のパラメータバインディング使用 |
| XSS 対策 | フロントエンドでの出力エスケープ（React のデフォルト）+ CSP ヘッダー設定 |
| CSRF 対策 | SameSite=Strict Cookie + カスタムリクエストヘッダー検証 |
| HTTPS 強制 | Nginx で HTTP → HTTPS リダイレクト。HSTS ヘッダー設定 |
| レートリミット | Nginx + FastAPI の2段階でレート制限 |
| 監査ログ | 全注文操作をタイムスタンプ・IPアドレス付きで記録 |
| シークレット管理 | 全APIキー・DBパスワードを環境変数で管理（.env は Git 管理外） |
